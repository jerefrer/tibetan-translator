3. **D3 Search does not re-run the query shown: done**, `8c44c2f` fix(search): keeps the results and their scroll when you come back to the same query. The route watcher skips the search when the query is the one whose results are shown. It still runs it when the enabled dictionaries in Settings changed since that search, when the query is another one, and when `all-terms-updated` or `dictionaries-updated` fired since (both mean the packs changed). Two things had to go with it for the results to really come back as they were:
   - The Dictionaries menu is read again from Settings each time the page shows (`DictionariesMenuMixin.activated`), which dropped its counts; Search now recounts them from the kept results (`resetDictionariesToDefaultAndSetNumberOfEntries`, what a new search did anyway, so a dictionary switched off in the menu for one search is reset to the Settings choice, as before).
   - On a phone the whole page scrolls, field included, so focusing the field on return scrolled back to the top. The field is now focused with `preventScroll` on return (`UiTextField.focus()` passes its options through). The focus still lands in the field.
   Checked in the browser: after scrolling "wisdom" to 150 results (1440) / 100 (390) and going to Define and back, no SQL ran, the same number of results was shown and the scroll was the same (results list at 7,200 px on desktop, the page at 7,200 px on the phone). Tests: `search-page.test.js`, "Search — coming back to the page": same query kept (results, number shown, menu counts), same query reached through `/search`, focus without scrolling, re-run after a change of enabled dictionaries, re-run for another query, re-run after `all-terms-updated`, re-run after `dictionaries-updated`, no second re-run once it ran for changed packs.

## Decisions for the owner

1. **D4, the underline of Tibetan hits.** I took "highlights" to include it, so in dark it is amber like the Latin hits. Options: keep it amber (as now); keep the logo yellow for the underline only.
2. **D5, the merge buttons are 30 px wide, not 44.** A wider area would cover the button of the next lane (30 px apart) and the divider. Options: keep 30 × 44 (as now); widen the lanes to 44 px, which is a visual change to the brackets.
3. **D7, Split's "Split" eyebrow.** When the text area is empty, the visible "Split" label above it and the hidden `h1` both say "Split", so a screen reader reads it twice. Options: keep (as now); hide the eyebrow from assistive technology (`aria-hidden`); make the eyebrow itself the `h1` while it is shown.
4. **D13, the tooltip.** I added the keys to the handle's tooltip ("Drag to reorder, or Alt+Up / Alt+Down") so sighted keyboard users can find them, since there is no Settings help. Options: keep; revert to "Drag to reorder"; add a Settings help, or a line in the card's subtitle ("Drag to reorder, switch off the ones you do not want").
5. **D13, macOS.** Alt is Option on a Mac; Option+Up / Down is what the code listens for. VoiceOver users usually interact with a control first; whether VoiceOver passes Option+Arrow through to the page was not checked. An alternative is Up / Down buttons on each row (the audit's second option), which needs no shortcut.
6. **D3, other changes that a kept result list does not see.** The results are kept unless the dictionaries switched on in Settings, the query or the packs changed. A dictionary **reordered** in Settings needs no new search: the kept results are re-sorted in the new order. An edit to My glossary that does not fire `all-terms-updated` / `dictionaries-updated` would show the old results until the next search; I did not trace whether every glossary save fires one.
7. **D3, the menu's temporary choices.** Dictionaries switched off in the Search menu for one search are reset to the Settings choice on return, as the re-run did before. Options: keep (as now); keep those choices too, which would be a new behaviour.
8. **ScanViewer** has its own copies of the "visually hidden" rules (`.scan-hidden-description`, `.scan-image-wrapper.visually-hidden`). I left them alone, as not part of D7; they could use `ui-visually-hidden`.

## Not verified

- **D14 in a browser.** The pack card renders only where packs are modular (the Tauri app). The Tauri IPC mock of the hardening audit is not in the repository and I did not rebuild it, so D14 rests on its unit tests: the focus is checked on the real component with a pack manager mock that behaves as the real one (the downloading state is set as soon as Install is pressed). Nor was the visible focus ring on the status line seen; no stylesheet removes the browser's own ring.
- **The Tauri app** on macOS, Windows, Linux, iOS and Android, and **WebKit / WebKitGTK**: only Chromium was used. In particular `min()` in a flex `width` (D1), `inset: min(...)` on a pseudo-element (D5), `focus({ preventScroll })` (D3, supported by Safari since 15).
- **Real touch** on the D5 hit areas: measured with `elementFromPoint`, not tapped on a device.
- **Screen readers:** the D7 headings, the D13 names, description and live announcement, and the D14 focus were checked in the DOM and by tests, not by listening with VoiceOver, NVDA or TalkBack.
- **Text sizes other than 100%** for D5: the clear button and thumb areas are written to reach 44 px and to add nothing once the control is larger, but were measured only at 100%.
- **D3 with the optional packs:** a real pack install or removal between two visits to Search was not tried (only the core pack was loaded); the events it depends on were fired in tests.
- **Glossary** (Tauri only): its search field uses the same clear button as the others, so D5 applies there too, unseen.
